# KafkaExample

## Test Type
Testbed Use

## Overall Description
An example of using Kafka to stream semi-real-time analysis out of a test, built around a manual RvR
test (a configurable list of attenuation steps run against a single STA). The traffic itself is
secondary -- the actual point of this script is to demonstrate the pattern for getting custom,
near-real-time data (plots and raw data alike) out of a running test via Kafka, so you can build your
own live dashboard or custom report on top of it.

The pattern has two halves, both demonstrated here:

**1. Producing a custom external data stream, in parallel with the test (`getDUTstats.py`).**
At each attenuation step, before starting traffic, the script launches `getDUTstats.py` as a separate
subprocess. That script polls the DUT directly (here, Calix-specific SSH/exec commands, as a stand-in
for whatever your own external data source might be) once every 5 seconds, in its own independent
loop, for as long as the subprocess stays alive. Each time it gets a new reading, it:
* Builds an ad hoc histogram and pie chart of the RSSI values seen so far (using Expert Analysis'
  `createHistogramFrom` endpoint) and a simple line plot of the raw values, assembles all three into a
  single report-JSON, and publishes that to the Kafka topic `plotStream`.
* Also publishes the raw RSSI data points (not just the plots) to a separate topic, `dataStream`, so a
  consumer can do its own processing on the underlying numbers rather than only the rendered plots.

Once traffic for that attenuation step finishes, the main script kills the subprocess and consumes
whatever's on `dataStream` to pull the live-collected DUT RSSI back into its own results (averaged in
as `aveDutRssi` for that attenuation step) -- showing the round trip: a side process produces data
independently, and the main script later consumes it back.

**2. Producing a live-updating version of the "real" report (`KafkaExample.py` + `createReport.py`).**
After every attenuation step (and again at the very end), the script calls
`createReport.summarize()` -- the same function that builds the final HTML report -- and publishes
*that* report-JSON to `plotStream` as well. A dashboard subscribed to `plotStream` would see the report
take shape step by step as the test runs, rather than only getting a finished report at the end.

## Executable Code
### KafkaExample.py
This is the main code. As always, it does the initial configuration: reading in the configuration
files, reading in the testbed configuration, setting up the directory for output files, etc. It also
sets up the Kafka producer (for `plotStream`/`dataStream`) and consumer (for `dataStream`) used
throughout the test, and drives the per-attenuation-step loop described above.

### getDUTstats.py
Not a Script Manager automation script -- a standalone helper, launched as a subprocess by
`KafkaExample.py` and killed once each attenuation step's traffic finishes. It's the concrete example
of "produce custom data/plots to Kafka": swap out the Calix-specific polling commands for whatever
your own external data source is, keep the same "build a report-JSON, `producer.send('plotStream',
...)`, publish the raw data to `dataStream` too" pattern, and you have your own live custom-data feed.

### createReport.py
Provides two entry points, both used here: `analyze()` (runs one result archive through Expert
Analysis -- zip2csv/getStats/objectify/crunch -- for a single attenuation step) and `summarize()`
(reads the accumulated result log and builds the full report: RSSI vs. Time/Attenuation, Throughput
vs. Time, and a 2x2 grid of MCS/NSS/Data Rate/Bandwidth, Tx vs. Rx). Both the HTML file it writes to
disk and the live Kafka publishing of its output are already wired up -- this file didn't need
changes for this script to work.

## Configurability
Configurable files are always, by default, params_test.json, and params_system.json.
params_system.json is for overall system configuration (IP addresses, DUT security, etc.)
params_test.json is for changes made to the test itself.

Key configuration includes: `primaryChannel`/`bw`/`interface`/`direction` (channel/bandwidth/PHY
mode/traffic direction), `palToUseSTA`, and `steps` (the comma-separated list of attenuation values to
step through). `getDUTstats.py`'s DUT polling target (`urlIP`) and Kafka broker address
(`localhost:9092`, used in both files) are hardcoded rather than read from params_test.json --- worth
pulling out into configuration if you adapt this for a different setup.

## Output
This test produces the standard CSV/JSON/zip output (one archive per attenuation step), plus the HTML
report generated by `createReport.summarize()`. In addition -- and this is the part worth trying out
if you're learning from this example -- the evolving report and the live DUT RSSI data are published
to the `plotStream` and `dataStream` Kafka topics throughout the run, not just written to disk at the
end. Point a Kafka consumer at either topic while the test is running to see this in action.
