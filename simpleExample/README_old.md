# simpleExample

## Test Type
Testbed Use

## Overall Description
A simple test that sets up one traffic pair and one sniffer, and runs traffic while doing a packet
capture. It illustrates all of the basic building blocks used by most automation scripts: setting up
the results file folder and names, setting attenuators, setting up a traffic pair, setting up and
associating an STA, and setting up, starting and stopping sniffing.

Assumes the DUT is in Box A, and the sniffer and STA STApals are in Box C.

At a high level, the script:
* Reads test parameters and sets up the results directory and result-log file for the run.
* Sets the quad attenuator(s)/MPE(s) to the configured value(s).
* Configures a single STA (optionally using a second Pal as a soft-AP instead of the real DUT).
* Sets up one traffic pair, in the configured direction (uplink or downlink) and iperf mode (TCP/UDP).
* Optionally sets up a sniffer for packet capture (enabled by default).
* Waits for the STA to associate with the AP.
* Starts the sniffer (if enabled), runs the traffic, then stops the sniffer and saves the capture.
* Collects average throughput and mean management RSSI results and logs them to the test result JSON.
* Optionally performs a second packet capture a few seconds after the first one completes, as an
  illustration of how to do so.
* Retrieves a time-aligned JSON export (and, optionally, a PDF report) from the Octobox REST API.
* Generates the final HTML report via `createReport.py`.

## Executable Code
### simpleExample.py
This is the main code. As always, it does the initial configuration: reading in the configuration
files, reading in the testbed configuration, setting up the directory for output files, etc.
All test-specific logic — configuring the attenuators, STA, traffic pair and sniffer, running the
test, and collecting the throughput/RSSI results — is done in this code.

### createReport.py
Run automatically at the end of the script. Reads the result-log JSON produced above, along with the
raw JSON result archive (analyzed via Expert Analysis), and produces the final HTML report: an RvR
throughput plot, an RvR RSSI plot, and time-series plots of average throughput, PHY rate, MCS,
bandwidth, and spatial streams (UL and DL).

## Configurability
Configurable files are always, by default, `params_test.json`, and `params_system.json`.
`params_system.json` is for overall system configuration (IP addresses, DUT security, etc.).
`params_test.json` is for changes made to the test itself.

This test has a fair amount of configurability in `params_test.json`, including:
* `primaryChannel`, `bw`, `iface`, `nss` — the channel, bandwidth, 802.11 protocol version, and
  number of spatial streams to use.
* `palToUseSTA` — which STApal to use as the test STA.
* `ulDl`, `iperfMode`, `trafficType`, `trafficBW`, `length`, `parallel`, `window` — the direction and
  characteristics of the traffic pair.
* `quadAttenStart`, `quadAttenStop`, `step`, `stepDuration`, `settlingTime`, `trainingInterval` — the
  attenuation sweep range and timing.
* `runPcapAnalysis`, `palToUseSniffer`, `snifferBW`, `headersOnly`, `managementOnly` — whether to run
  packet capture at all, and if so, which STApal to use as the sniffer and how to configure it.
* `doSecondCapture` — whether to also perform the illustrative second packet capture.
* `doPDF` — whether to also generate a PDF report at the end of the test.
* `usePalAsAP`, `palAPssid`, `palAPsecurity`, `palAPpassword`, `palAPchannel` — optionally use a
  second Pal as a soft-AP instead of testing against the real DUT.

SSID, security mode, and password are not configured in `params_test.json` — they're taken from
`params_system.json`'s `dut` block (per-band `ssid<band>`/`dutsecurity<band>`/`dutpass<band>` keys).

## Output
This test produces the standard CSV/JSON/pcap output, plus the HTML report (and, optionally, a PDF
report) generated by `createReport.py`. No further analysis beyond what's built into the report is
performed.
